# 00 使用說明——給任何接手這個專案的AI看

如果你是被叫來「重建」或「接手開發」財智管家 FinPilot 這個專案的AI（不管是Claude、GPT、Gemini或任何其他模型），**先看這份文件，再看下面三份，理論上就能在最少來回、不用重新踩坑的狀況下完成95%以上的工作**。

## 這一組文件有什麼、怎麼讀

按這個順序讀：

1. **這份文件（00）**——你正在讀的，說明怎麼用其餘三份。
2. **`01_主要Schema.sql`**——資料庫的完整現況。在全新的 Supabase 專案上從頭到尾執行一次，就會得到跟正式站一樣的資料庫結構。不用管歷史上的8個零散migration檔案怎麼演變過來的，這份是最終結果。
3. **`02_功能規格_完整版.md`**——系統現在的樣子，照模組整理（帳號、帳本、交易、財富管家、出差行程...），不是開發日記。每個模組都寫了「非顯而易見的規則」——這些通常是本來會這樣做、但實測後發現有問題才改掉的地方，直接照常識重新實作大概率會重新踩到同一個坑。
4. **`03_環境建置SOP.md`**——從空白的 GitHub/Supabase/Vercel 帳號開始，一步一步建好整個運作環境的操作清單，包含哪幾步是「AI不管用什麼工具都沒辦法自動完成、一定要人手動點一次Dashboard」的步驟。

## 這一組文件**不是**什麼

- **不是原始碼的替代品**。原始碼（`index.html`/`app.js`/`styles.css`）本身永遠是最終的、唯一不會錯的規格——這幾份文件是幫你在「看懂為什麼長這樣」跟「找到該改哪個函式」上省時間，不是拿來憑空重寫一份新程式碼。真的要動手改功能時，去讀對應的函式，不要只憑這份文件的文字描述就開始寫。
- **不是取代 `CLAUDE.md`**。`CLAUDE.md` 是持續更新的「工作日誌」，照時間順序記錄每次工作階段做了什麼、使用者當時的反應是什麼、後來又怎麼調整。這份日誌保留了更多「當時為什麼這樣決定」的脈絡細節與使用者原話，`02_功能規格_完整版.md` 則是把最終結論整理成「現在長怎樣」，兩者互補：
  - 想知道「現在這個功能應該怎麼運作」→ 看 `02`
  - 想知道「這個決定當初是怎麼來的、使用者原本的反應是什麼」→ 看 `CLAUDE.md`
  - **之後每次工作階段結束，`CLAUDE.md` 一樣要持續更新；但如果某個決定已經很穩定不會再變，應該同時回頭更新 `02` 對應章節，讓它保持跟現況同步，不要讓兩份文件的說法兜不起來。**

## 「95%」是什麼意思、剩下的5%是什麼

跟著這三份文件，一個新的AI應該可以：
- 不用問使用者任何架構性問題，就直接動手建資料庫、寫程式碼、串接服務
- 不會重新犯本專案已知的12+項技術陷阱（RLS+GRANT分離、datetime-local時區問題、CSS zoom縮放問題等）
- 知道每個功能「應該」長什麼樣子，可以直接對照驗收

無法100%自動化、一定要真人（帳號擁有者本人）介入的部分：
- Supabase Dashboard的「Exposed schemas」設定（沒有任何API能做到，一定要人手動點）
- 真實的 Supabase URL / API Key、GitHub repo權限、Vercel帳號授權——這些帳密性質的資訊本來就不該寫進文件裡，要接手的人自己去申請/取得
- 使用者尚未做出決定的產品方向（例如`02`文件第17節列的「已知限制」，是不是要解決、什麼時候解決，是業主決策不是技術問題）

## 如果要重建一個一模一樣的環境，最快路徑

1. 讀這份文件（已經在做了）
2. 把程式碼(repo)複製到新的GitHub repo
3. 照 `03_環境建置SOP.md` 從步驟1做到步驟7
4. 對照 `03` 文件最後的「完成後驗收清單」逐項打勾
5. 有任何行為對不上預期，回 `02_功能規格_完整版.md` 找對應模組章節，比對函式名稱去原始碼確認

## 如果是要在既有環境上繼續開發新功能

1. 讀 `02_功能規格_完整版.md`，了解現有架構跟已經踩過的坑（尤其第18節「跨模組共通的實作原則」）
2. 需要異動資料庫時，新的SQL還是照舊習慣寫成一份新的`docs/supabase-xxx.sql`（不要直接改`01_主要Schema.sql`本身，那份是「重建用的最終快照」，等這次改動穩定確認不會再變之後，再回頭把異動內容整併進`01`，讓它繼續保持「跑一次就是現在的完整現況」）
3. 功能做完、使用者驗收確認後，比照過去的習慣更新 `CLAUDE.md`（工作日誌），如果是會影響現有模組行為的決定，也同步回頭更新 `02` 對應章節
